# Контракт: слой общения с llama-server

Реализация — `backend/llm/client.py`. Обоснование каждого решения — [`../plan.md` §4](../plan.md#4-слой-llm).

> Всё в этом файле проверено запросами к живому llama-server
> (`experiment-streaming/llama_nothink_probe.py`, `llama_structured_nothink.py`,
> `llama_prefill_probe.py`). «Правильный» по документации вызов здесь местами даёт HTTP 400 —
> см. §2. Отклоняться от контракта без нового замера нельзя.

---

## 1. Два пути вызова

Класс `LlamaClient` предоставляет ровно два публичных метода. Третьего пути нет.

```python
class LlamaClient:
    async def stream_answer(
        self, messages: list[Message], *, max_tokens: int, temperature: float
    ) -> AsyncIterator[str]:
        """Свободный текст. /v1/chat/completions, stream=True, ризонинг подавлен."""

    async def decide(
        self, prompt: str, schema: dict, *, max_tokens: int = 256
    ) -> dict:
        """Решение агента. Сырой /completion + json_schema. Ризонинг невозможен."""
```

| | `stream_answer` | `decide` |
|---|---|---|
| эндпоинт | `POST /v1/chat/completions` | `POST /completion` |
| стриминг | да | нет |
| подавление ризонинга | предзаполненный assistant-тёрн | GBNF-грамматика с первого токена |
| `cache_prompt` | `true` | `true` |
| применение | текст ответа собеседнику | interject, barge-in, классификация намерения |

## 2. `stream_answer` — свободный текст

### Тело запроса

```jsonc
{
  "messages": [
    { "role": "system",    "content": "<стабильная часть: роль, правила сценариев>" },
    { "role": "user",      "content": "<RAG-контекст, история диалога, текущий транскрипт>" },
    { "role": "assistant", "content": "<think>\n\n</think>" }   // ← ОБЯЗАТЕЛЬНО, последний
  ],
  "stream": true,
  "cache_prompt": true,
  "temperature": 0.7,
  "max_tokens": 500
}
```

**Предзаполненный `<think>\n\n</think>` в последнем assistant-тёрне — единственный рабочий
способ подавления ризонинга.** Не альтернатива, а требование: без него первые ~2.5 с потока —
рассуждение, которое нельзя отдать в TTS, и весь выигрыш от стриминга исчезает.

Проверено и **не работает** — не пробовать заново:

| способ | что происходит |
|---|---|
| `chat_template_kwargs.enable_thinking = false` | no-op: 902 симв. рассуждения, побайтово как по умолчанию |
| `/no_think` в system | ризонинг остаётся |
| `reasoning: off` во флагах сервера | раскладывает в `reasoning_content`, генерировать не перестаёт |

### Ответ

SSE-поток. Отдавать в TTS **по законченному предложению**, а не по токену и не по всему
ответу: межтокенный интервал 10.56 мс, первое предложение готово за 0.1–0.3 с против 1.82 с
на полный ответ в 150 токенов.

Граница предложения — `. ! ? …` плюс перевод строки, но не внутри числа и не после
общепринятого сокращения. Логика нарезки — в `tts/text_normalize.py`, рядом с нормализацией.

### Отмена

Прерывание генерации — закрытие SSE-соединения (`httpx` `aclose()`). Накопленный текст
**не коммитится** в память диалога, если аудио ещё не пошло (FR-12). Никакой межпоточной
синхронизации: накопление живёт на event loop.

## 3. `decide` — решения агента

### Почему сырой `/completion`

На `/v1/chat/completions` structured output и подавление ризонинга **конфликтуют**:

| попытка | результат |
|---|---|
| `json_schema` без подавления | 1399–1418 симв. ризонинга, до JSON не доходит, упирается в `max_tokens` |
| `json_schema` + предзаполненный `<think></think>` | **HTTP 400** `Failed to initialize samplers: Unexpected empty grammar stack after accepting piece: <think>` |
| `response_format: json_object` + предзаполнение | 400 нет, но грамматика не применяется: markdown-проза, `<think></think>` возвращается в `content` |

Причина 400: GBNF-грамматика применяется ко **всему** assistant-тёрну, включая
предзаполненный текст, а `<think>` — не валидный JSON.

На сыром `/completion` грамматика ограничивает поток с первого токена, и модель физически не
может начать `<think>`. Проверено: 0.732 с и 0.461 с на двух кейсах, оба ответа схемно и
семантически корректны.

### Тело запроса

```jsonc
{
  "prompt": "<промпт целиком, включая разметку чата вручную>",
  "json_schema": { /* см. §4 */ },
  "cache_prompt": true,
  "temperature": 0.0,
  "n_predict": 256
}
```

`temperature: 0` — решения должны быть воспроизводимыми: одна и та же ситуация обязана давать
один и тот же вердикт, иначе поведение агента нельзя ни отладить, ни принять по A-06/A-07.

## 4. Схемы решений

`backend/llm/schemas.py`. Поле `reason` обязательно везде — оно уходит в телеметрию и в
панель «Технические данные», без него разбор поведения на записи невозможен.

### 4.1 `InterjectDecision` — вмешаться в затянувшуюся речь (FR-07)

```json
{
  "type": "object",
  "properties": {
    "interject": { "type": "boolean" },
    "understood": { "type": "string", "description": "что агент понял из речи на данный момент" },
    "reason":     { "type": "string" }
  },
  "required": ["interject", "understood", "reason"]
}
```

### 4.2 `BargeInDecision` — уступить перебивающему (FR-13)

```json
{
  "type": "object",
  "properties": {
    "interrupt": { "type": "boolean" },
    "reason":    { "type": "string" }
  },
  "required": ["interrupt", "reason"]
}
```

### 4.3 `IntentDecision` — понятен ли вопрос (FR-21, FR-22)

```json
{
  "type": "object",
  "properties": {
    "intent":     { "enum": ["question", "clarification_needed", "goodbye", "smalltalk", "unclear"] },
    "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
    "query":      { "type": "string", "description": "переформулированный запрос для RAG; пусто, если RAG не нужен" },
    "reason":     { "type": "string" }
  },
  "required": ["intent", "confidence", "reason"]
}
```

`intent` и `confidence` — **единственный** источник условий `intent == …` и
`confidence < …` в `dialogue/scenarios.yaml`. Никаких других «оценок намерения» в системе нет.

## 5. Промпт для решения о перебивании

Состав входа задан требованием FR-14 дословно. Порядок — по правилу «волатильное в конец»
(§4.3 замеров), поэтому первые три блока стабильны между вызовами и переиспользуют KV-кэш:

1. **Инструкция** (стабильна) — «определи, требует ли собеседник прервать твою речь».
2. **История диалога** до момента, когда мы начали формировать ответ (стабильна на всё время
   этого ответа).
3. **Формируемый ответ** целиком (стабилен: он уже сгенерирован).
4. **Доля озвученного** — «озвучено 4.1 с из 9.7 с (42 %)».
5. **Что собеседник говорит сейчас** — самый свежий частичный транскрипт с момента начала
   перекрытия.

Пункты 4–5 меняются, они и должны быть последними. Хвост в десятки токенов стоит ~67 мс
против полного пересчёта промпта.

Явное указание в инструкции: **поддакивание перебиванием не является.** Проверено, что модель
это различает — «ага… понятно… да» даёт `interrupt: false`, «нет, подождите, я про другое
хотел спросить» даёт `true`.

## 6. Раскладка промпта и prefill

Общая для обоих путей. Порядок — от стабильного к волатильному:

```
system: роль, правила поведения, правила сценариев        ← не меняется за сессию
────────────────────────────────────────────────────────
RAG-контекст (10 чанков)                                  ← меняется на запрос
────────────────────────────────────────────────────────
история диалога                                           ← растёт в конец
────────────────────────────────────────────────────────
текущий транскрипт (докладывается по ходу речи)           ← растёт в конец
────────────────────────────────────────────────────────
короткая инструкция / схема (десятки токенов)             ← хвост
```

- `cache_prompt: true` на **всех** вызовах.
- Обновление транскрипта — дописывание в конец, никогда не переписывание середины.
  Замер: 8–23 токена на обновление, ~60 мс, независимо от длины транскрипта.
- Хвост после транскрипта держать в пределах ~50 токенов. Инструкция в 2000 токенов после
  волатильной части превратила бы каждое обновление в пересчёт 2000 токенов.
- История диалога усекается **с головы**, а не с хвоста: усечение хвоста рушит кэш целиком.

## 7. Правила конкурентности

Из §4.6 замеров: два одновременных llama-вызова дают ×2.09 замедления основного стрима,
межтокенный p99 растёт с 13 мс до 79 мс.

- **`decide` никогда не вызывается в цикле.** Только по событию от не-LLM гейта.
- Одновременно с активным `stream_answer` допускается **не более одного** `decide`.
  Реализуется семафором на 1 в `LlamaClient`; попытка второго — ошибка, а не ожидание в
  очереди: если решение опоздало, оно уже не нужно.
- `-np 2` на сервере существует ровно под эту пару «стрим + одно решение», а не под
  параллельную нагрузку.

## 8. Флаги llama-server

Единственный источник правды — `scripts/serve-models.{ps1,sh}`. Здесь для сверки:

```bash
# LLM
llama-server -m Qwopus3.5-4B-Q4_K_M.gguf --host 127.0.0.1 --port 20099 \
  -ngl 99 -c 32000 -np 2 -fa on --jinja --no-webui

# Эмбеддер
llama-server -m bge-m3-Q8_0.gguf --host 127.0.0.1 --port 20100 \
  --embedding -ngl 99 --no-cache-prompt -cram 0 -ctxcp 0 -cpent -1

# Реранкер
llama-server -m bge-reranker-v2-m3-Q8_0.gguf --host 127.0.0.1 --port 20101 \
  --reranking -ngl 99 --no-cache-prompt -cram 0 -ctxcp 0 -cpent -1
```

Кэш промпта на энкодерах отключён намеренно: с включённым llama-server сохраняет кэш на
каждый чанк и перечитывает его целиком при каждом обновлении — на прогоне сетки сервер умирал
с HTTP 500 примерно на 784-м тексте из 5856.

`--reasoning off` **не ставится**: он лишь перекладывает рассуждение в `reasoning_content`,
создавая ложное впечатление, что проблема решена. Настоящее подавление — в §2.
