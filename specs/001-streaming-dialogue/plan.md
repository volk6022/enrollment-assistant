# План реализации: потоковый диалоговый ассистент

**Фича:** `001-streaming-dialogue` · требования: [`spec.md`](./spec.md)

Здесь — **как** устроена система. Каждое нетривиальное решение снабжено ссылкой на замер
в [`docs/streaming-research-findings.md`](../../docs/streaming-research-findings.md),
из которого оно следует. Решения без такой ссылки — это либо прямое требование заказчика,
либо следствие формальной модели, и это отмечено явно.

> **Читать перед тем, как писать код.** Раздел [§4 «Слой LLM»](#4-слой-llm) содержит три
> ограничения, которые нельзя вывести из документации llama.cpp и которые ломают реализацию,
> если их не знать. Они стоили отдельных экспериментов.

## 1. Топология процессов

```
┌──────────────────────────────────────────────────────────────────────┐
│ Браузер                                                              │
│   GUI (React + Vite)                                                 │
│   микрофон → AudioWorklet → PCM16 16 кГц → WebSocket                 │
│   WebSocket → очередь PCM → AudioWorklet → динамики                  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ WebSocket /ws/dialogue
┌───────────────────────────────▼──────────────────────────────────────┐
│ backend (docker, один python-процесс, asyncio)                       │
│                                                                      │
│   event loop ── WebSocket, VAD, таймеры, автомат, память диалога     │
│        │                                                             │
│        ├─ пул «stt»   (1 воркер) → faster-whisper на CUDA            │
│        ├─ пул «tts»   (1 воркер) → silero v5.5 на CPU                │
│        └─ пул «rag»   (1 воркер) → FAISS + BM25, вызовы энкодеров    │
│                                                                      │
│   httpx (на loop, без потоков) ──────────────┐                       │
└──────────────────────────────────────────────┼───────────────────────┘
                                               │ HTTP, хост-сеть
┌──────────────────────────────────────────────▼───────────────────────┐
│ хост (НЕ в docker) — поднимается scripts/serve-models.ps1|sh         │
│   llama-server :20099  Qwopus3.5-4B-Q4_K_M   -np 2  -c 32000         │
│   llama-server :20100  bge-m3 GGUF Q8_0      --embedding             │
│   llama-server :20101  bge-reranker-v2-m3 Q8 --reranking             │
└──────────────────────────────────────────────────────────────────────┘
```

**Почему монолит.** GIL оказался не блокером: whisper, silero и клиент llama-server его
отпускают, максимальный разрыв event loop в POC — 8–36 мс (§1, §6). Отдельные
whisper-/silero-серверы писать не нужно (§8.1). Единственный внешний процесс — llama-server.

**Почему llama-server снаружи docker.** Решение заказчика: в проде инференс-сервер чужой,
и его эндпоинт — параметр, а не наша ответственность. Следствие: `docker-compose up -d`
поднимает backend и GUI, а веса и llama-server — отдельный шаг, описанный в README (FR-31).
`docker-compose.yml` ходит на хост через `host.docker.internal` (для Linux добавляется
`extra_hosts: ["host.docker.internal:host-gateway"]`).

**Настоящее узкое место — не GIL, а GPU.** За него конкурируют три потребителя: частичные
транскрибации, генерация ответа и вспомогательные решения LLM. Дерутся при этом не все со
всеми: whisper и llama-server уживаются, а душат друг друга **два одновременных
llama-вызова** (§8.6). Отсюда весь §4.4 ниже.

## 2. Модель потоков и разделяемого состояния

Прямо из §7 замеров. Отступление от этой раскладки — регрессия, а не вкусовщина.

| что | где исполняется | почему |
|---|---|---|
| сокеты, VAD, таймеры, автомат, память | главный поток (loop) | всё дешёвое и асинхронное |
| whisper (GPU) | **свой** пул, 1 воркер | отпускает GIL; свой пул — чтобы не встать в очередь за TTS |
| silero (CPU) | **свой** пул, 1 воркер | отпускает GIL; на CPU ни с кем не конкурирует |
| эмбеддер + реранкер | пул «rag», 1 воркер | сериализация, чтобы не рвать VRAM |
| LLM | не поток — `httpx` на loop | чистый I/O |

**Пулы обязаны быть раздельными и однопоточными.** Общий пул означает, что синтез встанет
в очередь за транскрибацией — ровно та задержка, ради устранения которой всё переписывается.
Больше одного воркера на пул бессмысленно: и GPU (§2), и llama.cpp (§4.6) всё равно
сериализуют, лишние воркеры дадут только контеншен.

**Правило разделяемого состояния: мутируем на loop, в поток отдаём снимок.**

- Аудио-кольцо пишется на loop под `threading.Lock`; в whisper-поток уходит
  `np.concatenate(...)` — **копия**. Поток никогда не видит мутирующий объект, поэтому гонок
  нет by construction.
- Лок нужен именно потому, что запись — read-modify-write. Для полей, которые присваиваются
  целиком (последний транскрипт, состояние автомата), GIL достаточно.
- История диалога, тайминги, буфер транскрипта трогаются **только на loop**. Из потоков
  возвращаются голые значения, а не объекты состояния.
- Отмена генерации — это просто «не закоммитить накопленное» (FR-12). Межпоточная
  синхронизация не требуется, потому что накопление идёт на loop.

**Прогрев.** whisper прогревается **из своего воркер-потока** на старте, не из главного:
иначе разовая инициализация CUDA (128–1000 мс) переезжает в первый живой запрос (§8.9).

## 3. Аудио, VAD и транскрибация

### 3.1 Кольцевой буфер

- Длина **60 с** (`AUDIO_RING_SECONDS`), PCM16 моно 16 кГц, пишется непрерывно с момента
  открытия сессии и **никогда не останавливается** (FR-09).
- Все тайминги в системе — оффсеты в миллисекундах от `t0` = старт сессии. Единая ось
  времени, к которой привязаны и реплики собеседника, и наше воспроизведение.

### 3.2 VAD и отметка начала речи

Детекция начала речи опаздывает на десятки-сотни миллисекунд. Поэтому (FR-05):

1. VAD (Silero VAD на CPU, дёшево) работает по кольцу непрерывно.
2. При переходе «тишина → речь» ставится отметка `speech_start_ms` **назад** на
   `VAD_PREROLL_MS` (по умолчанию 300 мс) от момента срабатывания.
3. Транскрибация читает кольцо **с этой отметки**, а не с момента срабатывания.
4. Конец хода — `VAD_SILENCE_END_MS` = 500 мс тишины (FR-06).

### 3.3 Частота частичных транскрибаций — жёсткий потолок

У faster-whisper нет нативного стриминга: каждое частичное распознавание — повторный прогон
по накопленному окну. GPU их **сериализует**: 4 одновременных вызова заняли 1.202 с против
0.302 с у одного, ускорения от параллелизма нет (§2).

Следствия, обязательные к реализации:

- Не чаще `STT_PARTIAL_MAX_HZ` (по умолчанию **2.5** в секунду) и **только при активном VAD**.
- В любой момент времени в полёте **не более одного** прогона whisper. Пришло время
  следующего, а предыдущий не вернулся — такт пропускается, а не ставится в очередь.
- Окно прогона — `STT_WINDOW_SECONDS` (по умолчанию 15 с) от `speech_start_ms`; при более
  длинной речи окно скользит с перекрытием `STT_OVERLAP_SECONDS` (2 с).
- Финальный полный прогон по концу хода — за флагом `STT_FINAL_PASS`, **по умолчанию
  выключен**: последний частичный обычно даёт тот же текст и экономит ~310 мс из 877 мс
  (§8.10, OQ-03).

Без этого потолка распознавание задушит генерацию ответа — это не теория, это §2.

### 3.4 Синтез

Silero v5.5 **на CPU** (§3: RTF 0.066, 15× реалтайма; VRAM освобождается под whisper).
Оговорка из §3: `silero_cuda` показывает 0.028 с чистого GPU-времени, но в живом прогоне тот
же вызов занял 0.491 с — на коротких вызовах доминируют питоновские накладные расходы. CPU и
на бумаге достаточен, и на практике предсказуемее.

Перед синтезом текст проходит нормализацию чисел и латиницы — **переносится как есть** из
`services/voice-gateway/app/text_normalize.py` (коммит 166e190).

Синтез вызывается **только через `run_in_executor`**. В текущем коде
(`services/voice-gateway/app/main.py:95,197`) он вызван синхронно внутри `async def` и
блокирует loop на всё время синтеза — это ошибка, которую нельзя перенести в новый сервис
(§8, «Текущий код»).

## 4. Слой LLM

Три ограничения ниже добыты экспериментами и не следуют ни из какой документации.

### 4.1 Ризонинг гасится единственным способом

Qwopus3.5-4B — reasoning-модель. При стриминге первым в поток идёт `<think>`, и «первое
предложение» оказывается рассуждением, а не тем, что можно отдать в TTS.

Проверено всё (§4.3, temperature 0, один вопрос):

| способ | ризонинг | до первого **произносимого** токена |
|---|---|---|
| `/completion` без шаблона | есть | не дождались за 200 токенов |
| `/v1/chat/completions` по умолчанию | 902 симв. | ~2.5 с |
| `chat_template_kwargs.enable_thinking=false` | **902 симв., байт в байт то же** | ~2.4 с |
| `/no_think` в system-промпте | есть | ~2.8 с |
| **assistant-тёрн, предзаполненный `<think>\n\n</think>`** | **0 символов** | **0.075 с** |

`enable_thinking=false` для этого шаблона — **no-op**: llama-server лишь перекладывает
рассуждение в поле `reasoning_content`, генерировать его модель не перестаёт. Разница между
0.075 с и 2.5 с — это фактически весь бюджет латентности проекта.

### 4.2 Structured output и подавление ризонинга несовместимы на chat-эндпоинте

Проверено отдельно (`experiment-streaming/llama_structured_nothink.py`), потому что все
решения агента идут через structured output, а ризонинг гасить обязательно — и оба механизма
нужны одновременно (§4.5):

| способ | результат |
|---|---|
| `json_schema` без подавления | 1399–1418 симв. ризонинга, до JSON не доходит — упирается в `max_tokens` |
| `json_schema` + предзаполненный `<think></think>` | **HTTP 400** `Unexpected empty grammar stack after accepting piece: <think>` |
| `response_format: json_object` + предзаполнение | 400 нет, но грамматика не применяется: markdown-проза, `<think></think>` возвращается в `content` |

Причина 400: GBNF-грамматика применяется ко **всему** assistant-тёрну, включая предзаполненный
текст, а `<think>` — не валидный JSON.

**Отсюда — два непересекающихся пути вызова.** Полный контракт: [`contracts/llm.md`](./contracts/llm.md).

| что | эндпоинт | как гасим ризонинг |
|---|---|---|
| свободный текст ответа | `/v1/chat/completions`, `stream: true` | предзаполненный assistant-тёрн `<think>\n\n</think>` |
| любое решение агента | сырой `/completion` + `json_schema` | грамматика с первого токена — модель физически не может начать `<think>` |

Оба пути совместимы с `cache_prompt: true`. Проверено на живых кейсах: «нет, подождите, я про
другое хотел спросить» → `{"interrupt": true}` за 0.732 с; «ага… понятно… да» →
`{"interrupt": false}` за 0.461 с. То самое различение, которое требуется по FR-13/FR-17.

### 4.3 Инкрементальный prefill и раскладка промпта

Ключевая гипотеза плана подтверждена (§4.1). С `cache_prompt: true` llama-server
переиспользует KV-кэш неизменного префикса и досчитывает только дельту:

| шаг | символов в транскрипте | префилл, токенов | wall |
|---|---|---|---|
| 0 (холодный) | 12 | 517 | 0.228 с |
| 1 | 30 | **8** | **0.060 с** |
| 5 | 114 | 23 | 0.063 с |

Скорость префилла — **2391 tok/s**, в 2.4 раза выше искомых ~1000. Стоимость обновления —
фиксированные **~60 мс** независимо от длины транскрипта.

**Правило раскладки, обязательное для всех шаблонов: всё меняющееся — как можно позже.**
llama.cpp находит общий префикс и пересчитывает всё, что после точки расхождения. Хвост после
транскрипта допустим, пока он мал: фиксированная инструкция в 34–53 токена стоит ~67 мс
вместо полного пересчёта 550. Если бы после транскрипта стояло 2000 токенов инструкций,
каждое обновление транскрипта стоило бы 2000 токенов (§4.2).

Порядок в промпте — от стабильного к волатильному:
`system` → правила сценариев → RAG-контекст → история диалога → **текущий транскрипт** →
короткая инструкция/схема.

### 4.4 Конкурентные вызовы и приоритет GPU

Два одновременных llama-вызова душат друг друга (§4.6): основной стрим один — 1.821 с,
он же с классификатором рядом — **3.802 с** (×2.09), межтокенный p99 вырос с 13 мс до 79 мс.

Оговорка честная: классификатор опрашивался агрессивно, 12 вызовов за 3.8 с. Это **верхняя
оценка ущерба**, а не цена разового вызова (OQ-01). Но направление однозначно:

- **Классификатор перебивания опрашивается ровно один раз**, по событию от дешёвого не-LLM
  гейта: VAD говорит «речь» **и** длительность перекрытия > `DIALOGUE_BARGE_IN_OVERLAP_S`
  **и** осталось > `DIALOGUE_BARGE_IN_MIN_TAIL_S` (FR-13, FR-17).
- Никакого периодического опроса LLM ни для каких решений. Все решения — событийные.
- `-np 2 -c 32000` (решение заказчика): второй слот существует для **разового**
  вспомогательного вызова рядом с генерацией, а не для параллельной нагрузки.

## 5. Память диалога

Полный контракт и алгоритм сборки: [`contracts/memory.md`](./contracts/memory.md).

Коротко, что должно получиться (FR-18…FR-20):

- Единая ось времени от `t0`. Реплики собеседника получают оффсеты из таймингов whisper;
  наши — из момента старта воспроизведения плюс фактическая длительность отданного аудио.
- Реплики **могут перекрываться**, и история обязана это показывать — иначе LLM рассуждает
  над последовательностью, которой не было.
- Частично озвученный ответ хранится с долей озвученного (FR-16). Выброшенный черновик не
  хранится вообще (FR-12) — это инвариант `inv_dropped_never_committed` в формальной модели.
- Буфер транскрипта — 5000 символов, с тайм-кодами кусочков, **без** содержимого RAG-чанков.

## 6. RAG

Переносится из текущего кода (`rag/`), меняются только параметры и бэкенды.

| параметр | значение | источник |
|---|---|---|
| `RAG_TOP_K` | **10** | сетка 1200 тестов: значимый прирост chunks_score против k=5 (парный t=2.12, Δ=0.033±0.016); k=15/20 не окупают +1.8/+3.6 с префилла |
| эмбеддер | bge-m3 **GGUF Q8_0** через llama-server | §5.1; косинус к torch fp16 = 0.9993 |
| реранкер | bge-reranker-v2-m3 **GGUF Q8_0** | §5.1; spearman к torch = 0.9905, качество финальных ответов неразличимо (t=0.35) |
| `RAG_FUSED_TOP` | 50 | как в текущем проде |

**Обе RAG-модели остаются на GPU.** Переезд на CPU закрыт: реранкер ×122 медленнее
(35 с против 289 мс на 50 парах), эмбеддер терпим на запросах (×9), но переиндексация на CPU
нереальна — часы вместо минуты (§5).

Единственное исключение по GIL за весь ресёрч: **реранкер на CPU GIL держит** (разрыв loop до
100 мс, вероятно питоновская обвязка `CrossEncoder.predict`, а не матмуль). Практического
значения не имеет — вариант мёртв и без GIL, — но если реранкер когда-нибудь поедет на CPU,
его придётся выносить в процесс (§5).

**Флаги llama-server для энкодеров.** Кэш промпта на энкодерах отключается полностью:
`--no-cache-prompt -cram 0 -ctxcp 0 -cpent -1`. Без этого llama-server сохраняет кэш на
каждый чанк и перечитывает его целиком при каждом обновлении — на прогоне сетки сервер
умирал с HTTP 500 примерно на 784-м тексте из 5856.

## 7. Автомат и сценарии

**Автомат** — [`specs/formal/dialogue.qnt`](../formal/dialogue.qnt), диаграмма и разбор
неочевидных решений — [`specs/formal/STATE_MACHINE.md`](../formal/STATE_MACHINE.md).
8 состояний, проверено Apalache исчерпывающе: 8 инвариантов держатся, все состояния
достижимы, тупиков нет.

Модель **первична**. Расхождение кода с ней — баг кода. При изменении логики диалога сначала
правится `.qnt`, прогоняются `verify.ps1` и `reachability.ps1`, и только потом код.

Модель checker уже нашла одну дыру в требованиях: перекрытие поверх короткого хвоста не было
описано ни одним правилом, и агент вис с недоигранной репликой. Закрыто через FR-15.

**Реализация — LangGraph.** Одна нода на состояние, включая `ended`. Переходы — через
`add_conditional_edges` (не `add_edge`: у `add_edge` нет параметра `condition`). Каждое
ребро графа обязано соответствовать ровно одному `action` из `.qnt`.

**Сценарии** — [`dialogue/scenarios.yaml`](../../dialogue/scenarios.yaml). Редактируются без
правки кода (FR-24). Словарь условий и действий, который сценарии имеют право использовать,
задан в самом файле и реализуется в `backend/dialogue/scenarios.py`; загрузчик **падает на
старте**, если сценарий ссылается на неизвестное условие или действие — молча игнорировать
опечатку в YAML нельзя.

## 8. GUI

React + Vite, отдельный контейнер, отдаётся nginx. Baseline функционала —
[`docs/gui-spec-current.md`](../../docs/gui-spec-current.md); из него переносится **всё**:

с развёрнутым JSON (§6), работа с микрофоном и аудио (§7), светлая/тёмная тема по
`prefers-color-scheme`.

Добавляется поверх baseline:

- Захват микрофона через `AudioWorklet` → PCM16 16 кГц → WebSocket непрерывным потоком.
- Потоковое воспроизведение ответа: входящие PCM-чанки в очередь `AudioWorklet`, без ожидания
  полного файла. Немедленный сброс очереди по команде агента (обрыв приветствия, уступка).
- Индикация состояния автомата и потокового транскрипта.

## 9. Файловая структура и адаптеры

Фиксируется заранее, чтобы агенты не расходились в именах.

```
backend/
├── app.py                     # FastAPI: /ws/dialogue, /health, /metrics; сборка зависимостей
├── config.py                  # pydantic-settings, единственное место чтения .env
├── audio/
│   ├── ring.py                # AudioRing: кольцо 60 с, запись на loop под Lock, snapshot()
│   ├── vad.py                 # VadGate: silero-vad, speech_start_ms с преролом
│   └── clock.py               # SessionClock: единая ось времени от t0
├── stt/
│   └── whisper_worker.py      # WhisperWorker: свой пул 1 воркер, троттлинг, прогрев из потока
├── tts/
│   └── silero_worker.py       # SileroWorker: свой пул 1 воркер, CPU, нормализация текста
│   └── text_normalize.py      # перенос из services/voice-gateway/app/text_normalize.py
├── llm/
│   ├── client.py              # LlamaClient: два пути вызова (§4.2), cache_prompt, httpx
│   ├── prompts.py             # шаблоны; волатильное в конце (§4.3)
│   └── schemas.py             # json_schema для решений: InterjectDecision, BargeInDecision
├── rag/                       # перенос существующего rag/, бэкенды энкодеров на GGUF
│   ├── engine.py
│   └── gguf_encoder_client.py
├── dialogue/
│   ├── machine.py             # DialogueMachine: LangGraph, ноды 1:1 с dialogue.qnt
│   ├── nodes.py               # реализации нод
│   ├── scenarios.py           # ScenarioRegistry: загрузка + валидация scenarios.yaml
│   ├── memory.py              # DialogueMemory: сборка переплетённой истории
│   └── models.py              # DialogueTurn, DialogueState, Draft, RagResult
└── ws/
    └── session.py             # DialogueSession: один сокет = одна сессия, оркестрация
```

### Соответствие модели и кода

| в `dialogue.qnt` | в коде |
|---|---|
| `AgentState.Greeting … Ended` | `dialogue.models.AgentState` (та же восьмёрка) |
| `Draft.NoDraft/Building/Voicing/Dropped/Committed` | `dialogue.models.Draft` |
| `action greetingPlays` и остальные 23 | ребро в `DialogueMachine`, имя метода = имя действия |
| `turnLen / idleLen / overlapLen / speechLeft` | `DialogueState.timers`, в **миллисекундах** |
| `TALK_LIMIT / IDLE_LIMIT / OVERLAP_LIMIT / TAIL_MIN` | `.env`: `DIALOGUE_INTERJECT_AFTER_S` / `_IDLE_HANGUP_S` / `_BARGE_IN_OVERLAP_S` / `_BARGE_IN_MIN_TAIL_S` |

Пороги в модели **порядковые** (мелкие границы нужны, чтобы Apalache проверял исчерпывающе);
реальные секунды живут только в `.env`.

## 10. Бюджеты

### VRAM (§5.2, §7)

| компонент | 8 ГБ dev (дефолт) | 12 ГБ прод |
|---|---|---|
| llama-server 4B Q4_K_M | 4307 МБ @ `-c 16k -np 2` | то же, `-c 32k` — больше |
| whisper large-v3-turbo int8 | 1240 МБ | 1240 МБ |
| bge-m3 | **GGUF Q8_0** ~474 МБ | fp16 ~1130 МБ |
| bge-reranker-v2-m3 | **GGUF Q8_0** ~510 МБ | fp16 ~1130 МБ |
| **итого** | **6531 МБ**, запас ~1.6 ГБ | ~7.8 ГБ, запас ~4 ГБ |

Полный torch-стек — 7810 МБ — **в 8 ГБ не влезает** без запаса на пики и фрагментацию.
Цена выбора «всё GGUF» — реранк 521 мс против 289 мс. На dev-боксе это принято (решение
заказчика: «на моём пк всё в q8 в gguf»).

Внимание при подъёме `-c` до 32000: KV-кэш растёт, и 4307 МБ измерены на `-c 16k`. На 8 ГБ
это надо перемерить перед тем, как считать конфигурацию рабочей.

### Латентность

| участок | замер | источник |

## 11. Docker

```yaml
services:
  backend:    # python-процесс из §1; сеть — bridge + host.docker.internal
  gui:        # nginx со сборкой Vite
```

- llama-server **не в compose** (решение заказчика). Поднимается на хосте
  `scripts/serve-models.ps1` / `scripts/serve-models.sh`; флаги — единственный источник
  правды по портам и параметрам.
- GPU в backend-контейнер пробрасывается для whisper/silero:
  `deploy.resources.reservations.devices` + `NVIDIA_VISIBLE_DEVICES`.
- Веса монтируются volume'ом из `MODELS_DIR`, **не** скачиваются (FR-31).
- `/health` проверяет реальную достижимость трёх llama-эндпоинтов и загруженность whisper и
  silero, а не просто «процесс жив».
- README: ссылки на веса, порядок запуска, минимум VRAM (FR-30, FR-31).

## 12. Тестирование

| уровень | что покрывает | где |
|---|---|---|
| формальный | автомат: инварианты и достижимость | `specs/formal/verify.ps1`, `reachability.ps1` |
| unit | переходы автомата 1:1 с `.qnt`; валидация сценариев; кольцо и VAD-преролл; сборка переплетённой истории | `tests/unit/` |
| контрактный | оба пути LLM против **живого** llama-server: подавление ризонинга, `json_schema`, `cache_prompt` | `tests/contract/` |
| интеграционный | приёмочные A-01…A-11 на заранее записанных аудио | `tests/integration/` |
| нагрузочный | разрыв event loop < 50 мс (NFR-04) под STT+TTS+LLM одновременно | `tests/load/` |

Контрактные тесты обязательны: §4.2 показывает, что «правильный» по документации вызов даёт
HTTP 400. Такое ловится только реальным запросом, моком — никогда.
